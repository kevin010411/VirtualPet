# 電子雞跨層功能開發流程

記錄日期：2026-10-10。

本文件記錄本專案採用的功能開發順序與完成判準。前端負責創作者的編輯方式，後端負責驗證與匯出，韌體負責設備上的執行行為。前端提出編輯方式時，應同步確認韌體可行性，並在正式實作前共同確認資料契約。

本文件只記錄協作流程，不取代功能規格。跨層功能的權威規格留在 Web 儲存庫；本韌體專案記錄韌體實作安排與驗證證據。既有 Pet Stats／Behavior／Action／Status／Evolution／持久化等契約仍以 `E:\C++\virtualPet\web\.scratch\sd-driven-pet-stats\spec.md` 為準，不在此複製。

## 一 觀察需求並確認功能缺口

以使用者操作與設備行為描述需求，不先以圖片、欄位或類別名稱代替功能。若有 HTML 模擬器或既有產品，先實際操作，記錄進入、操作、返回、退出、結果與例外行為，再對照現有系統支援範圍。

文件描述、截圖或素材只能作為線索。尚未觀察或尚未核對現有實作的項目標記為待確認，不能直接當成已確認的功能缺口。

產出：經使用者確認的功能清單、可觀察的行為與證據、目前支援程度、尚待確認的問題。

## 二 使用者決定優先級

功能清單確認後，由使用者決定優先級與本批範圍，再將結果記錄。可以提出相依關係與取捨，但不能把建議順序當成使用者已批准的優先級。

每個項目至少記錄：功能名稱、缺口描述、HTML 操作情境或其他證據、影響層、前置依賴、使用者決定的優先級、狀態與驗收條件。尚未排定的優先級填「待使用者決定」。

## 三 前端提出編輯方式並確認韌體可行性

先確認創作者需要設定什麼，以及設備使用者會如何操作。可以用草圖或小型原型討論編輯方式，但在正式完成前端前，同步確認以下事項：

- 按鍵與時間需求，例如短按、長按、計時與回合判定。
- 顯示需求，例如版面切換、動畫、訊息與數值更新。
- 固定容量、Flash／RAM、資源讀取與必要的持久化資料。
- 功能應由通用能力承擔，還是由特定遊戲規則承擔。

產出：確認後的編輯方式、設備行為、可行性限制與責任邊界。未確認的限制須保留，不以完整前端實作掩蓋。

## 四 共同確認資料契約

前端、後端與韌體共同確認欄位、型別、預設值、範圍、容量、參照身份、執行順序、錯誤處理、版本與舊資料處理方式。

不只確認「匯出資料格式是否改變」，也要確認「資料的執行語意是否改變」。即使欄位保持相同，按鈕從播放動畫改為進入子選單，仍是需要確認的行為變更。

產出：一份權威功能規格與跨層契約；韌體文件引用它，只補充本層的實作與驗證。

## 五 按完整功能分批實作

每批完成一條可驗收的流程：前端可編輯、後端可驗證並匯出、韌體可讀取並執行。例如先完成一層子選單的設定、匯出、進入與返回，再擴充其他流程。

前端與韌體可在契約確認後按依賴安排工作，但不應先把所有前端設定做完，再集中處理尚未確認可行的設備能力。

## 六 使用同一份匯出資料驗收

依實際變更範圍執行前端、後端與韌體的必要檢查；變更匯出或資料契約時，加上跨層契約驗證。配對驗證使用同一 Project 的同一份匯出 bundle，確認設定內容與設備行為一致。

依專案既有驗證指引執行必要檢查與發布前完整驗證。記錄實際執行的檢查、結果與未驗收範圍；host 或建置通過不代表 SD／TFT／按鍵實機已通過。

## 完成狀態分開記錄

| 狀態 | 意義 |
| --- | --- |
| 素材可匯入 | 素材可以被編輯器讀取，不代表已有功能邏輯 |
| 編輯器可設定 | 創作者可以編輯並保存，不代表設備已支援 |
| 匯出契約已驗證 | 後端與韌體對資料及語意已有一致驗證，不代表實機已驗收 |
| 韌體功能已實作 | 設備執行邏輯已完成，仍須記錄相應驗證範圍 |
| 實機已驗收 | 配對素材與韌體在設備上通過約定的操作情境 |

各狀態不能互相代替；功能完成與尚未驗收的部分必須明確列出。
